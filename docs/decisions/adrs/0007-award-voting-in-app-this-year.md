# ADR 0007: 今年のアワード投票はアプリ内で実施する

- **日付:** 2026-09-10
- **ステータス:** 採用

## 状況

参加者向けのアワード投票画面（`src/features/award/pages/AwardVotePage.tsx`）とサンプル実装は
以前から存在したが、`/award-vote` ルートは `LegacyPlaceholderPage`（準備中）に向いており、
本番クライアント（`ApiParticipantClient.getAwardVoteSnapshot` / `saveVotes`）は空スタブだった。
一方でボトムナビとオンボーディングは「アワード投票」を案内し続けており、Q&A（PR #94）だけが
言及を消していた。「紹介はするが Q&A には無く、押すと準備中」という食い違いが残っていた。

今年アワード投票を実施するかどうかを決める必要があった（issue #89）。

## 決定

案 B を採る。**今年もアワード投票を実施し、アプリ内で完結させる。**
投票できるのは、その参加者が**チェックイン済みのブースだけ**。

- 「チェックイン済み」の照合は**サーバーで行う**（`POST /events/:id/awards/vote` が
  403 `NOT_CHECKED_IN` を返す）。UI が選択肢をチェックイン済みに絞るのは表示の都合であって関門ではない
- 投票は **`award_id` をキー**に保存する（賞名を直しても票が迷子にならない）
- `saveVotes` は全票を1回で送る（1票ずつのループにしない。途中失敗で部分保存が残る）
- 型は `Award` に1本化し、`VoteAwardCategory`（`shared/types/voteAward.ts`）は廃止
- 運営画面（`/admin/awards`）で賞ごとのブース別票数（降順）・賞の CRUD・投票の開閉（`manager` 限定）を行う。
  同数に順位は付けない
- API 契約の正本は `event-support-server/docs/specs/gacha-and-award/06-api/award-api.md`

## 結果

- `/award-vote` は参加者ゲートの内側のまま `AwardVotePage` に差し替えた（未認証で開けないこと）
- Q&A・オンボーディング・ボトムナビの3つが「実施する」で揃った
- `tests/unit/event-content-2026.test.ts` の禁止語から `アワード` を外した（去年の日程・運用の禁止語は残す）
- サンプルモード（`VITE_DATA_SOURCE=sample`）も同じ型・同じ `award_id` キーで動く

## 代替案（却下理由）

- **案 A: 今年は実施しない:** ナビ・オンボーディングから言及を消す掃除だけで済むが、
  実施可能な状態のコードを捨てることになるため — 却下
- **案 C: アプリ外の別手段で投票:** 外部フォームではチェックイン履歴と突き合わせられず、
  「行ったブースにだけ投票できる」という今年の方針が担保できないため — 却下
