# ADR 0005: スケジュール・Q&A は今年も静的な定数で持つ

- **日付:** 2026-09-05
- **ステータス:** 採用

## 状況

`ApiParticipantClient.getSchedule` / `getQa`（本番クライアント）は API を呼ばず、`sample/` 配下の定数
（`SAMPLE_SCHEDULE` ・ `SAMPLE_QA_ITEMS`）をそのまま返していた。定数の置き場が `sample/` だったため、
去年（2025-10-10/11・2日開催・スタッフ立会いあり）の内容がサンプルモードだけでなく本番にもそのまま
出続けていた。

今年（2026-10-16・1日開催）は運営体制も変わり、ガチャポンはアプリ内完結でスタッフの立会いを要さない。
去年の内容を差し替える必要があるが、当日のタイムテーブルは開催まで確定しないため、いったん空の状態で
リリースし、確定後に反映する二段構えが要る。また、当日はイベント運営中であり、当日中に main へマージ
してデプロイし直す運用は取らないため、当日にアプリ側でタイムテーブルを直すことはできない。

## 決定

C 案を採る。本番クライアント（`ApiParticipantClient`）とサンプルクライアント（`SampleParticipantClient`）
の両方が読む定数を `src/shared/data/content/eventContent2026.ts` に置き、`sample/` から出す。

- スケジュール（`SCHEDULE_2026`）・Q&A（`QA_2026`）は今年の内容のみを持つ。去年の内容は残さない
- 当日の変更はアプリではなく、会場の掲示・アナウンスで行う。運営にはサーバー側の
  `docs/operations/run-day-guide.md` §8 で周知する
- サンプルモードと本番が同じ内容になるのは意図的である（同じ定数を読むため、差分の出しっぱなしを防ぐ）

## 結果

- アプリ側での当日変更はできない。変更には再デプロイが要り、当日は main への直マージを行わないため、
  当日にタイムテーブルの誤りを直すことはできない
- スケジュールは運営から確定タイムテーブルを受領するまで `events: []` の空とし、参加者向けの画面には
  「タイムテーブルは会場の掲示・アナウンスをご覧ください」と表示する
- 確定タイムテーブルを受領した段階（段2）で `SCHEDULE_2026` を埋め、以後はアプリ内にも表示される

## 代替案（却下理由）

- **案 A: 定数の中身だけを今年の内容に差し替える（置き場は `sample/` のまま）:** 差し替えた事実・理由が
  コードにもドキュメントにも残らず、なぜ `sample/` に本番の定数が置かれているかという不整合も温存する
  ため — 却下
- **案 B: サーバー側に API を作り、運営が編集できる画面を用意する:** server 側の契約変更・マイグレーション・
  運営向け編集画面の新規実装が必要になり、残り開催までの期間に収まらないため — 却下
