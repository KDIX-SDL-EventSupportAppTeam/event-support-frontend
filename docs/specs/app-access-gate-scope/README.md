# アプリ公開ゲートの適用範囲

## 何が問題なのか

公開ゲート `RequireAppOpen` は **`/home` にしか掛かっていない。**
参加者向けの他の画面は、URL を直接開けば開放前でも触れてしまう。

```
/home        ← ゲートあり
/checkin     ← ゲート無し。開放前にチェックインできる
/booth-list  ← ゲート無し
/venue-map   ← ゲート無し
/gachapon    ← ゲート無し（/use /complete も）
/schedule    ← ゲート無し
/qa          ← 認証すら不要
```

**開放前のチェックインは実害がある。** ビンゴカードが発行され、中央マスが埋まり、
場合によっては解放と推薦まで走る。**当日データにイベント開始前の行が混ざる。**

## 決定

**参加者が触るすべての画面をゲート配下に入れる。**

| パス | 変更後 |
|---|---|
| `/home` | ゲートあり（変更なし） |
| `/checkin` | **ゲートを追加** |
| `/booth-list` | **ゲートを追加** |
| `/venue-map` | **ゲートを追加** |
| `/gachapon` `/gachapon/use` `/gachapon/complete` | **ゲートを追加** |
| `/schedule` | **ゲートを追加** |
| `/qa` | **ゲートを追加**（認証も要求する） |
| `/e` `/e/:eventId`（入口） | **掛けない。** 事前アンケートは開放前に回答するもの |
| `/verify-email` | **掛けない。** 開放前にメール確認を完了させる |
| `/exhibitor` | 掛けない（出展者向け） |
| `/admin/*` `/organizer/*` | 掛けない（運営・主催者） |

**入口とメール確認にゲートを掛けてはならない。**
掛けると事前アンケートに答えられなくなり、事前推薦マスの材料が集まらない。

## 実装のしかた

ルータで**まとめて**掛ける。1画面ずつ `RequireAppOpen` を書き足す形にしない。
書き足す形にすると、画面が増えたときに漏れる。

```
<Route element={<ParticipantLayout />}>
  <Route element={<RequireAuth><RequireAppOpen /></RequireAuth>}>
     ... 参加者画面をここに入れる
  </Route>
</Route>
```

**新しい参加者画面を足す人が、意識せずにゲート配下に入る構造にする。**

## 起きてはいけないこと

- **入口（`/e/:eventId`）にゲートが掛かること。** 事前アンケートが回答不能になる
- **ゲートで弾いた画面が真っ白になること。** 開放予定時刻の案内を出す（既存の表示を使う）
- **ゲートの判定をフロントで計算すること。** `is_open` はサーバーが返す

## テスト項目

- [ ] T-1 `is_open = false` のとき、上表の「ゲートを追加」の全パスが開放待ち画面になる
- [ ] T-2 `is_open = false` でも `/e/:eventId` が開き、事前アンケートに回答できる
- [ ] T-3 `is_open = false` でも `/verify-email` が動く
- [ ] T-4 `is_open = true` で全画面が従来どおり開く
- [ ] T-5 未認証で `/qa` を開くと入口へリダイレクトされる（**現在は開ける**）
- [ ] T-6 出展者・運営の画面はゲートの影響を受けない
- [ ] T-7 開放待ち画面に開放予定時刻が出る
