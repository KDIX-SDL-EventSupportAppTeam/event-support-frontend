# 手動テスト仕様書（Event Support App / 網羅版）

人が実際に画面を触って確認するための仕様書。上から順に実施すれば、主催者のイベント作成から
参加者の当日利用、運営の管理画面、片付けまでを 1 周する。

- 対象: `event-support-frontend`（React）+ `event-support-server`（Fastify / MySQL）
- 記録: 各表の「結果」欄に OK / NG、NG は「備考」に画面名・操作・実際の表示を書く
- 優先度: ★★★ = 必ず実施 / ★★ = リリース前に実施 / ★ = 余裕があれば

## 0. 事前準備

### 0-1. 環境

| 項目 | 値 |
|---|---|
| API | `http://127.0.0.1:3000/api/v1`（`localhost` は使わない） |
| フロント | `http://localhost:5173` |
| 必須の環境変数 | `VITE_DATA_SOURCE=api` / `VITE_MOCK_API=false` / `VITE_API_BASE_URL` |

サーバー側の起動。

```bash
docker compose up -d mysql
npm run db:seed
npm run dev
```

フロント側は別ターミナルで起動する。

```bash
npm run dev
```

DB を直接見る場合の接続。

```bash
docker compose exec mysql mysql -uroot -p event_support
```

#### 仕様書の前提と実装の食い違い（作成直後の公開ゲート）

仕様書は「新規イベントには公開ゲートの行が無く `closed` 扱い」という前提で書かれているが、
実装は **イベント作成時に `event_app_access` の行を作る**（`event-support-server/src/lib/app-access.ts:107`
`buildDefaultAccessDefaults`）。既定値は次のとおり。

| 項目 | 既定値 | 今回の実測値 |
|---|---|---|
| `mode` | `scheduled` | `scheduled` |
| `app_opens_at` | 開始日時の 30 分前 | `2026-09-12T08:30:00Z`（＝作成時点で既に過去。アプリは開放済み） |
| `pre_survey_closes_at` | 開催日の前日 23:59:59（JST 基準） | `2026-09-11T14:59:59Z`（＝既に過去。`is_pre_survey_open: false`） |

開始日時を当日にしてイベントを作ると、**事前アンケートが最初から受付終了**になり、参加者には
「事前アンケートの回答受付は終了しました。」が出る（`event-support-frontend/src/features/entry/steps/SurveyStep.tsx:68`）。
この状態では第 2 章（B-19 / B-20 / B-26）が実施できないため、イベント作成直後に主催者 API で
`{"mode":"closed","pre_survey_closes_at":"2026-09-13T14:59:59Z"}` に設定し直してから第 2 章を開始した。
コードは変更していない。仕様どおりの挙動ではあるが、当日にイベントを作る運用では躓く点なので三上くんへ申し送る。

また、新規イベントには**事前アンケートの設問が 1 件も入っていない**（`GET /events/:id/pre-survey/questions`
が `questions: []`）。そのため J-27（設問追加）を第 2 章の前に前倒しで実施した。

### 0-3. 注意

- 参加者が触る URL は `/e/:eventId` の 1 本だけ。段階ごとの URL は存在しない。
- ガチャコインの使用は取り消せない。消費される前提で進める。
- イベントデータ全削除は本当に全部消える。周回テストの最後にだけ使う。
- 評価の仕様は「チェックイン直後に、いま訪問したブースを評価する」に変更が決まっている。
  変更前の実装は「次のチェックインのときに 1 つ前のブースを聞く」。第 5 章を読んでから触ること。
  関連 issue: event-support-frontend#115 / event-support-server#133

## 5. 評価とコメント

**この章は評価フロー変更の中心。仕様を理解してから実施する。**

決定した仕様は次のとおり（event-support-frontend#115 / event-support-server#133）。

1. 評価は**チェックインした直後**に、**いま訪問したブース**に対して聞く。
2. **初回のチェックインでも評価モーダルが出る。**
3. モーダルに出るブース名は、**いまチェックインしたブース**。
4. その場で評価しなかったブースは、**ブース一覧とビンゴカードから後で評価できる**。
5. **評価済みのブースは二重に評価できない。** 導線を出さない、または評価済みと分かる表示にする。
6. 「1 つ前のブースを聞く」経路は使わない。

変更前の実装は、次のチェックインのときに 1 つ前の未評価ブースを聞いていた。
そのため初回で評価画面が出ず、モーダルの名前も前のブースだった。
未修正の状態でこの章を実施すると E-1 から E-9 が落ちる。それが変更前の挙動である。

`booth_ratings` を直接確認する場合の例。

```sql
SELECT r.id, r.rating, r.comment, r.booth_id AS rating_booth, c.booth_id AS checkin_booth,
       b.name AS booth_name, c.checked_in_at
  FROM booth_ratings r
  JOIN check_ins c ON c.id = r.checkin_id
  JOIN booths b ON b.id = r.booth_id
 ORDER BY c.checked_in_at DESC;
```

`rating_booth` と `checkin_booth` は常に同じ値になる。ここが食い違うならサーバー側の不具合、

## 発見した不具合・改善提案

### NG-1 イベントの開始日時・終了日時が +9 時間ずれる（不具合・三上へ依頼）

| 項目 | 内容 |
|---|---|
| ID | A-12 で発見（A-5 の入力に起因） |
| 画面 | 主催者ポータル / イベント作成・イベント詳細・イベント一覧 |
| 操作 | 新規作成で開始日時「2026/09/12 09:00」・終了日時「2026/09/13 18:00」を入力して作成し、イベント詳細を開く |
| 期待 | 「2026/9/12 9:00:00 〜 2026/9/13 18:00:00」と表示される |
| 実際 | 「2026/9/12 18:00:00 〜 2026/9/14 3:00:00」と表示される（どちらもちょうど +9 時間） |
| 再現性 | 1 回中 1 回（原因がコード上で確定しているため常時再現とみられる） |
| 端末 | Mac / Chrome |

原因（コードで確認済み）:

1. `event-support-frontend/src/features/organizer/pages/OrganizerEventCreatePage.tsx:72-73`
   `datetime-local` 入力の値（`2026-09-12T09:00`。タイムゾーン情報を持たないローカル壁時計）を変換せず
   `date_start` / `date_end` として送信している。
2. `event-support-server/src/routes/v1/organizer/events.ts:95-98`（`createEventBody`）は `z.string().min(1)` で
   受けるだけで、同 193 行の INSERT にそのまま渡す。DB には UTC の DATETIME として `2026-09-12 09:00:00` が入る。
3. 読み出しは同ファイル `toEventPayload`（85-86 行）が `toIso()` で末尾に `Z` を付け `2026-09-12T09:00:00Z` として返す。
4. 表示は `OrganizerEventDetailPage.tsx:110-111` と `OrganizerEventListPage.tsx:137-138` が
   `new Date(...).toLocaleString('ja-JP')` で UTC→JST に変換するため +9 時間になる。

つまり「JST として入力した値を UTC として保存し、UTC として読んで JST に直す」ため往復で 9 時間ずれる。

**表示だけの問題ではない。** 同じ未変換値が `event-support-server/src/lib/app-access.ts:95-134`
`buildDefaultAccessDefaults` にも渡るため、参加者向けアプリの開放ゲートが実際に遅れて開く。

| 影響 | 内容 |
|---|---|
| `app_opens_at`（機能不具合） | 常に意図より **+9 時間**。「開始 30 分前に自動で開く」が「開始の 8 時間 30 分後に開く」になる。今回の実測でも、開始 09:00 JST に対し `2026-09-12T08:30:00Z`（＝17:30 JST）が入った。正しければ `2026-09-11T23:30:00Z` |
| `pre_survey_closes_at` | 2 つの +9 時間シフトが打ち消し合うため、開始時刻が JST 15:00 未満なら結果的に正しい値になる。15:00 以降だとちょうど **+24 時間**（1 日）ずれる |
| 状態判定・残り時間 | 準備中→開催中、開催中→終了 の切り替わりが 9 時間遅れる。`shared/lib/eventStatus.ts:22-50`。一覧の絞り込み（A-19）、詳細・一覧・運営サイドバー・管理パネルのバッジと残り時間が同じだけずれる |
| 参加者の待機画面 | `features/entry/lib/formatOpenSchedule.ts:14` の「開放予定 M/D HH:MM」と `shared/hooks/useAppAccess.ts:39-40` のカウントダウンが誤る |
| JWT の有効期限 | `event-support-server/src/lib/jwt.ts:25-28` が `date_end + 86400 秒` で算出するため、意図より 9 時間長くなる（短くなる方向ではないのでログアウト事故は起きない） |

同じ「`datetime-local` の値を変換せず送る」パターンは他に無い（frontend 全体で `type="datetime-local"` は
`OrganizerEventCreatePage.tsx:175, 187` の 2 箇所だけ。運営画面にイベント日時の編集 UI は存在しない）。
`admin/events.ts` の PATCH と `organizer/app-access.ts` の PATCH は `isoToMysqlUtc()` で正しく正規化しており、
同じ壊れ方はしていない（ただし呼び出す UI が現状無い）。

seed イベント（`20000000-0000-4000-8000-000000000001`）は作成フォームを通っていない直書きのリテラルなので
**影響を受けていない**（`event-support-server/src/scripts/seed-dev.ts:221` 付近）。

修正は frontend だけでは足りない。`buildDefaultAccessDefaults` は受け取った文字列に無条件で末尾 `Z` を付けるため、
frontend を直して `Z` 付きの正しい ISO 文字列を送ると `...ZZ` という不正な文字列になり例外になる（実測確認済み）。
最小修正は次の 2 ファイルをセットで直すこと。

| repo / ファイル | 行 | 変更内容 |
|---|---|---|
| frontend `src/features/organizer/pages/OrganizerEventCreatePage.tsx` | 72-73 | `datetime-local` の値を JST の壁時計として解釈し、UTC の ISO 文字列に変換してから送る（例 `new Date(\`${form.dateStart}:00+09:00\`).toISOString()`）。`input` の `type` はそのままでよい |
| server `src/routes/v1/organizer/events.ts` | 193-194 / 202 / 234-235 / 244 | zod 検証後に `isoToMysqlUtc()` で正規化し、その値を INSERT と `buildDefaultAccessDefaults` の両方に使う（`admin/events.ts` の PATCH と同じ書き方）。`datetime.js` からの import が 1 行増える |

既存データの移行が要る。作成フォーム経由で作られたイベントは `date_start` / `date_end` が +9 時間ずれており、
`event_app_access` の `app_opens_at` も +9 時間、`pre_survey_closes_at` は開始が JST 15:00 以降のものが +24 時間ずれている。
本番（さくら）へ適用する場合は SQL を須藤先生に渡す運用になる。

既存テストはこの不具合を検出していない。`event-support-server/tests/unit/organizer-portal.test.ts:262-343` は
まさにバグの元になる生の `datetime-local` 形式（`'2026-08-01T10:00'`）をペイロードに使っているが、
モック DB が固定値を返すだけで INSERT パラメータの中身を検証していないため、固定も検出もしていない。
frontend には作成フォームの送信値を検証するテストが存在しない。

今回の E2E では修正せず三上くんへ申し送る。テストは、公開ゲートと事前アンケート締切を
主催者 API（正しく正規化される経路）で明示的に設定し直すことで影響を避けて続行した。
第 1 章 A-21 / A-22 の `scheduled` 検証も同じ API を使うため、この不具合の影響を受けない。
